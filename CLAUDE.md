# Contracter: правила работы для Claude Code

## Scope

Сейчас разрабатываются только PostgreSQL-база и Rust-crates `db` и `economy-core`. Не создавай и не изменяй backend, HTTP API, frontend или Steam-аутентификацию без отдельного прямого запроса пользователя.

Перед изменениями прочитай `README.md`, `docs/superpowers/specs/2026-09-13-database-economy-core-design.md`, относящийся к задаче план, текущий `Cargo.toml` и существующие тесты.

## Неприкосновенные правила данных

- Денежные значения хранятся целыми числами; вычисления не используют двоичный `float`.
- Ledger, история цен и административный аудит остаются append-only.
- Контракт принимает от 4 до 10 входных предметов включительно, все одинаковой редкости и все различные, и сохраняет данные для воспроизводимого результата. Правило «ровно 10» отменено `CONTRACTER_GAME_MECHANICS.md`; вероятности коллекций и float результата делятся на фактическое число входов, а не на константу.
- Повтор внешней операции должен быть безопасен за счёт idempotency key.
- Seed-скрипты должны быть идемпотентными.
- Не ослабляй ограничения базы ради прохождения теста.

## Миграции

Не редактируй опубликованные миграции `db/migrations/0001_*.sql`–`0005_*.sql`: SQLx проверяет их checksum. Каждое изменение схемы добавляй новой миграцией с очередным номером. Добавляй или обновляй SQL-инварианты в `db/tests/`, если меняется поведение схемы.

## Разработка и проверка

Сначала добавь тест, который подтверждает требуемое поведение, затем внеси минимальную реализацию. Не удаляй и не переписывай чужие незавершённые изменения без прямого разрешения.

Перед завершением выполни:

```bash
./scripts/verify.sh
git diff --check
git status
```

Без `TEST_DATABASE_URL` PostgreSQL-интеграция будет пропущена — не называй её проверенной. С реальной тестовой PostgreSQL скрипт также применяет миграции и seeds, запускает SQL-инварианты и ignored SQLx integration test.

## Секреты

Никогда не записывай в репозиторий Aiven Service URI, пароли, токены или заполненный `.env`. Для интеграционных тестов используй только переменные окружения `TEST_DATABASE_URL` и при необходимости `PGPASSWORD`. Не выводи их значения в логах и ответах.

## Git

Работай в отдельной feature-ветке, делай узкие коммиты и открывай Pull Request в `main`. Перед `git add` просмотри `git status`; не используй `git add .` вслепую, не делай force push в `main`.
