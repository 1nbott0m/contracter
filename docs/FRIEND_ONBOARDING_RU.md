# Как начать работу над Contracter

Эта инструкция предназначена для второго разработчика проекта. Сейчас мы работаем только над PostgreSQL-базой и Rust-crates `db` и `economy-core`. Backend и frontend пока не разрабатываем.

## 1. Подготовь доступ и инструменты

У тебя уже должен быть доступ к приватному репозиторию:

```text
https://github.com/1nbott0m/contracter
```

Проверь, что установлены:

- Git;
- стабильный Rust через `rustup`;
- Claude Code, если хочешь использовать подписку Claude;
- PostgreSQL client (`psql`) — только для полной проверки с настоящей PostgreSQL.

Проверка основных инструментов:

```bash
git --version
rustc --version
cargo --version
claude --version
psql --version
```

Отсутствие `psql` не мешает собирать проект и запускать обычные Rust-тесты. На macOS его можно установить пакетом `libpq` через Homebrew:

```bash
brew install libpq
```

Скрипт проекта сам найдёт стандартную Apple Silicon-установку `/opt/homebrew/opt/libpq/bin/psql`.

## 2. Склонируй репозиторий

```bash
git clone https://github.com/1nbott0m/contracter.git
cd contracter
```

Если GitHub запросит авторизацию, войди в свой GitHub-аккаунт через Git Credential Manager, GitHub CLI или SSH. Подписка Claude Code не предоставляет доступ к GitHub автоматически.

## 3. Сначала изучи проект

Прочитай в таком порядке:

1. `CLAUDE.md` — обязательные правила для Claude Code и разработчиков.
2. `README.md` — состав проекта и команды проверки.
3. `docs/superpowers/specs/2026-09-13-database-economy-core-design.md` — согласованная архитектура.
4. `docs/superpowers/plans/2026-09-14-sqlx-db-crate.md` — план реализации crate `db`.
5. `db/migrations/` и `crates/db/` — текущая реализация.

Документы `koncepciya-bazy-dannyh-cs2.docx` и `plan-razrabotki-sayta.docx` хранят исходную концепцию, но при работе с кодом ориентируйся также на актуальные Markdown-спецификации и существующие тесты.

## 4. Проверь исходное состояние

```bash
git status
./scripts/verify.sh
```

Без переменной `TEST_DATABASE_URL` скрипт проверит форматирование, Clippy, Rust-тесты и shell-скрипты, а PostgreSQL-интеграцию осознанно пропустит. Это нормальный результат для первого запуска.

## 5. Используй Claude Code

Запусти Claude Code только из корня репозитория:

```bash
claude
```

Для первого знакомства можно дать ему такой запрос:

```text
Прочитай CLAUDE.md, README.md, актуальную спецификацию базы и содержимое crates/db.
Ничего не изменяй. Кратко опиши архитектуру, действующие инварианты и команды проверки.
```

После этого давай Claude одну конкретную задачу за раз. Перед принятием результата всегда проси показать изменённые файлы и вывод проверок. Подписка Claude Code совместима с проектом: это обычный Rust workspace и PostgreSQL. Однако она не заменяет GitHub-доступ, Rust toolchain или доступ к базе Aiven.

## 6. Работай в отдельной ветке

Перед каждой задачей:

```bash
git switch main
git pull --ff-only
git switch -c feature/kratkoe-nazvanie-zadachi
```

После изменений:

```bash
./scripts/verify.sh
git status
git diff --check
git add ПУТИ_ТОЛЬКО_К_НУЖНЫМ_ФАЙЛАМ
git commit -m "feat: kratko opishi izmenenie"
git push -u origin feature/kratkoe-nazvanie-zadachi
```

Затем создай Pull Request в `main` и попроси второго участника проверить изменения. Не делай `force push` в `main` и не добавляй посторонние файлы через `git add .` без просмотра `git status`.

## 7. Правила изменения базы

- Не изменяй уже опубликованные миграции `0001`–`0005`: SQLx контролирует их checksum.
- Изменение схемы оформляй новой последовательной миграцией, например `0006_name.sql`.
- Денежные значения хранятся целыми числами, без `float`.
- Ledger, цены и административный аудит являются append-only.
- Контракт принимает ровно 10 предметов одинаковой редкости и сохраняет воспроизводимый результат.
- Seed-файлы должны оставаться идемпотентными.
- Новое поведение сначала покрывается тестом, затем реализуется.
- Не создавай backend/frontend-заготовки без отдельного согласования.

## 8. Секреты и Aiven

Никогда не коммить:

- пароль Aiven или PostgreSQL;
- Service URI;
- заполненный `.env`;
- вывод терминала, содержащий секреты.

Не используйте один пароль `avnadmin` вдвоём. Для совместной работы безопаснее локальная PostgreSQL у каждого разработчика. Если другу всё же нужен Aiven, владелец проекта должен создать отдельного PostgreSQL-пользователя с минимально необходимыми правами и передать пароль вне GitHub и репозитория.

Полная проверка с PostgreSQL запускается через `TEST_DATABASE_URL` по инструкции в `README.md`. После проверки очисти переменные:

```bash
unset PGPASSWORD TEST_DATABASE_URL
```

## 9. Первый рабочий день — короткий чек-лист

- [ ] Репозиторий клонирован, `git status` чистый.
- [ ] Прочитаны `CLAUDE.md`, `README.md` и спецификация базы.
- [ ] `./scripts/verify.sh` завершился без ошибок.
- [ ] Понятно, что сейчас в scope только база и экономическая логика.
- [ ] Для задачи создана отдельная ветка.
- [ ] Перед Pull Request выполнены тесты и просмотрен diff.
- [ ] В коммите нет паролей, URI Aiven и `.env`.

## 10. Твоё первое конкретное задание

После успешного первого запуска реализуй **read-only слой доступа к каталогу** в crate `db`. Это будет первая небольшая настоящая задача перед более рискованными операциями с инвентарём и ledger.

### Что должно появиться

1. Новый модуль `crates/db/src/catalog.rs`.
2. Публичные типы результата для:
   - коллекции (`id`, `public_id`, `slug`, `display_name`);
   - предмета каталога (`id`, `public_id`, коллекция, `rarity_code`, `stable_name`, границы float, `enabled`);
   - SKU (`id`, `public_id`, предмет, wear band, `enabled`).
3. Методы чтения через существующий `PgPool`:
   - получить коллекцию по `public_id`;
   - получить предмет каталога по `public_id`;
   - получить SKU по `public_id`;
   - получить все активные SKU заданной коллекции и редкости в стабильном порядке по `sku.id`.
4. Экспорт нового API из `crates/db/src/lib.rs`.
5. PostgreSQL integration tests в отдельном файле `crates/db/tests/catalog.rs`.

### Требования к реализации

- Используй SQLx и типизированные ID из `crates/db/src/ids.rs`.
- Для `numeric(9,8)` используй `rust_decimal::Decimal`, а не `f32`/`f64`.
- Запрос отсутствующего `public_id` должен возвращать `Ok(None)`, а не маскировать его под ошибку подключения.
- Список должен содержать только записи, у которых включены коллекция, предмет и SKU.
- Не добавляй cache, HTTP-слой, сериализацию JSON и бизнес-логику.
- Не изменяй миграции `0001`–`0005`: для этой задачи изменение схемы вообще не требуется.
- Не добавляй реальные модели скинов в постоянный seed. Тестовые коллекции, предметы и SKU создавай внутри тестовой транзакции и делай rollback.
- Не используй compile-time запросы, которым при сборке нужен настоящий `DATABASE_URL`. Тесты и сборка должны работать без секрета Aiven.

Если тип `Decimal` нужен напрямую, добавь `rust_decimal.workspace = true` только в `crates/db/Cargo.toml`.

### Сначала напиши тесты

Покрой как минимум следующие случаи:

1. Все три сущности находятся по существующему `public_id`.
2. Неизвестный `public_id` возвращает `None`.
3. Выборка по коллекции и редкости не возвращает отключённую коллекцию, отключённый предмет или отключённый SKU.
4. Результаты возвращаются в стабильном порядке по `sku.id`.
5. Decimal-границы float считываются без потери точности.

Интеграционные тесты, требующие PostgreSQL, пометь `#[ignore = "requires an isolated PostgreSQL database in TEST_DATABASE_URL"]` по примеру `crates/db/tests/postgres.rs`. Каждый тест должен самостоятельно подготовить нужные данные и не зависеть от порядка запуска других тестов.

### Проверка перед Pull Request

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
./scripts/verify.sh
git diff --check
git status
```

Если доступна отдельная тестовая PostgreSQL, дополнительно запусти полный `./scripts/verify.sh` с `TEST_DATABASE_URL`, а затем новые ignored tests. Не запускай destructive-тесты против общей или production-базы.

### Что прислать в Pull Request

- краткое описание добавленного API;
- список покрытых сценариев;
- точные команды проверки и их результат;
- честное указание, запускалась ли PostgreSQL-интеграция;
- отсутствие изменений вне `crates/db`, если они не были необходимы для этой задачи.

Задание считается готовым только когда обычные проверки проходят без `DATABASE_URL`, PostgreSQL-тесты проходят на изолированной тестовой базе, в diff нет секретов и второй разработчик одобрил Pull Request.
